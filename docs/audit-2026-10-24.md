# Audit of `next` — security, performance, maintainability

**Date:** 2026-10-24 · **Branch:** `next` @ `1c53cd8` · **App version:** 1.5.0+7 · **DB version:** 6

## Scope and method

Read-only review. No code was changed. Covered: `AndroidManifest.xml`, Gradle, Kotlin
`MainActivity`, backup rules, `lib/` (database, backup, auto-backup, deep links, share intake,
search, providers, screens, notifications), tests, CI, scripts and dependency state.

**Verified by running:** `flutter analyze` → no issues. `flutter test` → 158 passed.
`flutter pub outdated` reviewed.

**Not verified:** nothing was run on a device or emulator. Performance items below come from
reading code and are not profiled. I did not build the release APK, run `flutter analyze` on
`main`, or review the 59k-line scraper output. Treat performance numbers as hypotheses to measure.

## Summary

The app's security posture is good for an offline app. There is no `INTERNET` permission in the
main manifest, all SQL is parameterised, and external URLs are scheme- and host-checked and
confirmed first. The main risks are data-safety and robustness, not attack surface. The biggest
performance costs are reading whole 38 MB-database rows when only a few columns are needed, and
decoding a 2048×2048 hero image. The biggest maintenance gaps are English strings that bypass
l10n, a CI that does not cover `next`, and migration tests that only cover v5.

## Security and data safety

### S1 — A false "unusable" verdict would overwrite the user's database (High impact, low likelihood)
`database_helper.dart:63-89`. User data (notes, highlights, categories, links, and `is_favorite`)
lives in the same SQLite file as the bundled songs. If `_isDatabaseUsable` fails (the file is
corrupt, or `SELECT COUNT(*) FROM songs` throws for any reason, including a transient I/O or lock
error) the code deletes and re-copies the asset, and every user table goes with it. The only
recovery is the auto-backup restore. That restore is itself gated by a one-shot marker, so a
second wipe on the same device would not be restored.

Recommendations:
- Before re-copying, rename the old file to `thiruppugazh.db.corrupt-<ts>` instead of overwriting.
  If the copy succeeds, try to pull user tables back out of the old file with `ATTACH` (best
  effort).
- Treat "could not open" (I/O or lock) differently from "opened fine but has zero songs".
- Reset the restore marker when a re-copy happens, so a wiped DB can be restored again.

### S2 — Auto-backup snapshot is written in place (Medium)
`auto_backup_service.dart:110-118` uses `file.writeAsString`. If the process dies mid-write, the
single snapshot that Android Auto Backup will later restore is truncated. On the next fresh
install `maybeRestore` fails, logs, and still sets the one-shot marker, so the user's data is
lost for good. Write to `*.tmp`, `flush`, then `rename`. Optionally keep the previous snapshot as
`.bak` and try it if the primary fails to parse.

### S3 — Backup import validation gaps (Medium)
`backup_service.dart`
- `_validateBackupMap` checks `favorites` and `categories` thoroughly but only checks that
  `notes`, `highlights` and `links` are lists. Elements are then cast with `as Map`
  (`:386`, `:399`, `:448`). A malformed element throws inside the transaction. The transaction
  rolls back, which is the right outcome, but the user sees a generic failure and the whole
  import is lost. For links this is already handled per row (`importLinks`); notes and highlights
  should do the same: validate and count a bad row as "skipped".
- `categories[].name` is accepted at any length. The UI limit is 2–50 characters
  (`AppConstants.categoryMinNameLength` / `categoryMaxNameLength`) but import does not apply it.
  The same goes for note `content` and link `title`. Apply the same limits on import.
- No file size cap: `file.readAsString()` + `jsonDecode` on the main isolate. A multi-hundred-MB
  JSON would exhaust memory. Cap at a few MB before reading (a real backup is KBs).
- The `favorites` length cap (10,000) exists; add equivalent caps for the other lists.
- Auto-restore (`auto_backup_service.dart:130`) reads `jsonDecode(...) as Map<String, dynamic>`
  and calls `applyImport` without `_validateBackupMap`, so it skips the structural checks the
  manual path has. `_validateBackupMap` is private; make it shared.

### S4 — Exported backup stays in the cache directory (Low–Medium)
`backup_service.dart:168-172` writes `thiruppugazh_backup_<ts>.json` (all notes and links, in
plain text) to `getTemporaryDirectory()` and never deletes it. Other apps cannot read it, but it
lingers until Android trims the cache. Delete it after the share sheet returns (success or not).

### S5 — Privacy policy does not mention backup (Medium, compliance)
`privacy_policy_screen.dart` has no mention of Android Auto Backup (which uploads the notes,
highlights, links and settings snapshot to the user's Google account), nor of the export file.
The policy is also a hard-coded English screen (see M1). For a "no tracking, no accounts" app,
the backup behaviour should be stated plainly. Also check that the Play Console Data Safety form
matches.

### S6 — Raw exceptions shown in the UI (Low)
`home_screen.dart:78` (`'Error loading random song: $e'`) and `song_detail_screen.dart:200`
(`'Error updating favorite: $e'`) put exception text in a SnackBar. This can show file paths or
SQL messages. Show a localized generic message and log the detail.

### S7 — Deep links and share intake: checked, mostly fine
- `thiruppugazh://song/{id}` and `https://thiruppugazh.ayilavan.org/song/{id}` are parsed with
  `int.tryParse` and looked up by parameterised query; unknown ids are ignored. Good.
- Share intent: `LinkUtils.extractUrl` accepts only http(s); the user picks the song and the URL
  is re-validated on open. Good. The Kotlin side reads `EXTRA_TEXT` without a length limit; a
  huge shared string goes through the MethodChannel and into a regex. Truncate to e.g. 8 KB in
  `takeSharedText`.
- Hardening, optional: `_handleDeepLink` accepts `http` for the app-link host, but the manifest
  only declares `https`. Harmless; remove `http` for consistency. The `thiruppugazh://` custom
  scheme can be claimed by any other app, so never let it trigger anything beyond opening a song
  (true today).
- `autoVerify="true"` requires `/.well-known/assetlinks.json` on `thiruppugazh.ayilavan.org`
  with the **release** signing fingerprint. I could not check the live site from here; confirm it
  once per release or links fall back to the browser.

### S8 — Cloud backup content (Info)
`backup_rules.xml` / `data_extraction_rules.xml` include `auto_backup/` and all `sharedpref`.
Notes and links therefore go to the user's Google Drive backup. Android encrypts this end to end
only when the device has a screen lock. This is a reasonable default for the product; mention it
in the policy (S5). `android:allowBackup="true"` is intentional and documented.

### Checked and found sound
- No `INTERNET` permission in the main manifest; no analytics or tracking packages.
- All SQL uses `whereArgs`. The only interpolated SQL (`_tanglishNormalizedSql`, column names in
  `addLikeConditions`, `_addColumnIfMissing`) uses compile-time constants, not user input.
- External links: `_isValidUrl` allow-lists https + host for built-in sites; saved links go
  through `LinkUtils.isValidUrl`, are re-validated at open time and confirmed first, naming the
  site.
- Components: `MainActivity` is the only exported component; the notification receivers are
  `exported="false"`.
- Release build has `isMinifyEnabled` and `isShrinkResources` on. `key.properties`, `*.jks` and
  `*.keystore` are git-ignored and none are tracked.
- `android/app/proguard-rules.pro` is empty. That is fine today but will need keep rules if a
  reflection-based plugin is added; the release smoke test in CLAUDE.md covers this.

## Performance

### P1 — `SELECT *` on a 38 MB table (High)
The `songs` table holds full lyrics, meanings, words and `search_content` for every song. These
paths load all columns:
- `getSongsPaginated` (every home-list page, 50 rows).
- `getSongsByCategoryId`, `getSongsByTemple`, `getFavoriteSongs`: whole categories and temples,
  where list rows need only title, place, id and the favorite flag.
- `searchSongsWithFilter` and `getSongsByIds` (search results).
- `buildBackupJson` → `getFavoriteSongs()` (`backup_service.dart:135`) loads and JSON-decodes the
  **full text of every favorite just to read its id**. This runs on every debounced mutation
  (5 s after any change) and at startup.

Recommendations:
- `buildBackupJson`: add `getFavoriteSongIds()` (`SELECT id FROM songs WHERE is_favorite = 1`).
  This is the cheapest, safest win.
- Add a lightweight list projection (`id, title, english_title, place, english_venue, kaumaram_id,
  is_favorite`) for list and search screens; load the full `Song` only on the detail screen. This
  needs a `SongSummary` type or a nullable-field `Song`, so it is a bigger change than the first
  item.

### P2 — `Song.fromMap` decodes 11 JSON columns per row (Medium)
`song_model.dart:81-113`. Each row runs `jsonDecode` + `List<String>.from` on up to 11 columns,
on the UI isolate. For a 50-row page, or a category of several hundred songs, this is measurable
jank. P1's projection removes most of it; otherwise decode lazily (getters over the raw string) or
run in `compute()` for large lists. `Song.fromMap` also throws if any column holds malformed JSON,
which would blank an entire list; consider per-column try/catch.

### P3 — `ORDER BY RANDOM() LIMIT 1` (Medium)
`getRandomSong` (`database_helper.dart:944`) sorts all 1,340 wide rows. Pick a random offset
instead: `getSongsCount()` then `getSongByIndex(random)`; both already exist.

### P4 — Hero image (Medium, memory + APK size)
`assets/images/hero.png` is 2048×2048, 5.4 MB, shown at 350 px height
(`home_screen.dart:146`) with no `cacheWidth` or `cacheHeight`. Flutter decodes it at full size
(~16 MB of RAM) on first Home build. Re-export at about 1080 px as WebP (likely under 300 KB) and/or
pass `cacheWidth`. This is a visible startup and memory improvement for the smallest change.

### P5 — Search over unindexed text (Medium)
`searchSongsWithFilter` ORs `LIKE '%q%'` across `title`, `lyrics`, `words`, `pathavurai`,
`english_*` and a chain of 18 nested `REPLACE()` calls for the venue. That is a full scan of the
largest columns on every query (debounced at 500 ms). The in-memory index already ranks the top
results well. Options, in order of cost:
1. Run the "deeper" DB search only when the index returns fewer than N results, or only after the
   user pauses/submits.
2. Precompute a normalised `place_normalized` column in `build_db.py` (a bundled-data change; the
   schema change would need the usual migration path).
3. SQLite FTS5 over a content table. Large change; only if (1) is not enough.
Also: `LIKE` wildcards in the user's query (`%`, `_`) are not escaped, so typing `_` matches any
character. This is a correctness issue, not a security issue; add `ESCAPE '\'`.
Measure first: the existing test shows 50 index searches over 1,340 songs in 55 ms, so the
index is not the bottleneck; the DB query is the one to profile.

### P6 — Legacy migration assets ship to everyone (Medium)
`english_data.json` (6.7 MB), `mayuragiri_data.json` (3.5 MB) and the v5 patches are bundled and
parsed with `jsonDecode` on the UI isolate, but are used only when upgrading a DB older than
v3/v4. Fresh installs already get these columns from the bundled DB. They add roughly 10 MB
uncompressed to the app. If the minimum supported upgrade path can drop v1/v2 installs (check Play
Console data for installs below 1.2/1.3), these assets and migrations can be removed, or at least
decoded with `compute()`. Do not remove without that data: CLAUDE.md requires every upgrade path
to work.

### P7 — Smaller items (Low)
- `_initDatabase` opens the DB read-only and runs `COUNT(*)` on every launch before opening it
  again for real. Cheap, but on slow storage it delays first content. The count could be done in
  `onOpen`.
- `AppLogger` builds timestamps and level strings in release builds even though nothing is
  emitted; return early when not in debug.
- `SongRepository.notifyListeners()` after every write makes every `SongRepository` listener
  rebuild; check that screens use `Consumer`/`select` narrowly. `song_detail_screen.dart` calls
  `context.watch<LyricsFontSizeProvider>()` in three places, so the whole screen can rebuild on a
  font change; one at the top is enough.
- `DatabaseHelper.onMutation` fires once per row during an import transaction; the 5 s debounce
  absorbs it, but it will also fire for the restore itself, rewriting the snapshot right after a
  restore. Harmless, but suppress during `applyImport`.
- The startup auto-backup sequence runs while the first screens load. After a restore
  (`maybeRestore`), the already-built screens are not notified (`SongRepository.refresh()` is not
  called), so a freshly restored favorite list can look empty until the user navigates.
  **Worth verifying on a device**; I did not.

## Maintainability

### M1 — Hard-coded strings (Medium, violates the project convention)
CLAUDE.md requires every user-visible string in both ARB files. Found in `lib/`:
- `song_detail_screen.dart`: `'Invalid URL'`, `'Could not launch YouTube for …'`,
  `'Could not launch Google for …'`, `'Could not launch the custom URL'`,
  `'Could not launch Mayuragiri'`, `'Song … removed from Favorites'` / `'added to Favorites'`,
  `'Error updating favorite: $e'`.
- `backup_service.dart`: `'Export successful'`, `'Export failed. Please try again.'`, share
  `subject`/`text`, `'an unknown date'`.
- `home_screen.dart:78`, `settings_screen.dart:223` (`'Could not open GitHub repository'`) and
  `:286` (`'English'` as a language label, which is acceptable if intentionally untranslated).
- `privacy_policy_screen.dart`: whole screen, title `'Privacy Policy'`.
- `reminder_notification_service.dart` channel name and description (Android shows these in
  system settings).
Also: `settings_screen.dart:218-224` launches the GitHub URL **without** the confirm-first step
the conventions require ("always confirm first, naming the site"). `song_detail_screen.dart` does
confirm; Settings does not.

### M2 — Daily reminder time is wrong across DST (Medium)
`reminder_notification_service.dart:104`. The reminder is scheduled as a `TZDateTime` in
`tz.UTC` with `DateTimeComponents.time`. The repeat matches the **UTC** wall-clock time, so in
a region with daylight saving the reminder drifts by an hour when clocks change, and it does not
follow a user who changes time zone. The comment justifies UTC as avoiding a timezone-name
lookup. Fix options: add `flutter_timezone` (small, offline) and schedule in the local location,
or reschedule on every app start (`ReminderSettingsProvider` already knows the time) using the
local offset at that moment, which keeps the error to at most one DST period between launches.
Not a problem in India (no DST) but real for any other devotee abroad. **Not reproduced.** *Update:* `ReminderSettingsProvider` reschedules the reminder on every app launch, so the error lasts only until the app is next started. A true fix needs the new `flutter_timezone` dependency; left as is.

### M3 — CI and lints (Medium)
- `.github/workflows/ci.yml` triggers only for pushes and PRs to `main`. Work happens on `next`,
  so nothing is checked until the merge. Add `next` (and PRs into it).
- `flutter analyze --no-fatal-infos` is used with a note to remove it once infos are cleaned.
  Local analysis is now fully clean, so remove the flag.
- CI does not run Python script tests (`scripts/test_*.py`), `flutter gen-l10n`/ARB parity
  checks, or a release build. A small ARB-key-parity test (every key in `app_en.arb` exists in
  `app_ta.arb`) would enforce the l10n rule in M1.
- Consider enabling `flutter_lints` 6.x and a few extra lints (`unawaited_futures`,
  `use_build_context_synchronously` is already on via flutter_lints, `avoid_print` outside
  `AppLogger`).

### M4 — Upgrade-path tests (Medium)
`test/data/` has migration tests for v5 (`migration_v5_test.dart`, `migration_v5_real_db_test.dart`)
and the links table (`links_*`). CLAUDE.md requires testing upgrades from **every** earlier DB
version (v1→latest) with user data present, using the real bundled DBs from git history. There is
no v1→v6, v2→v6, v3→v6 or v4→v6 test in the tree. The doc `docs/crash-reporting-decision.md`
records a past incident in exactly this area. Add a parameterised test that checks out each
historical DB, seeds user data and compares user tables before and after.

### M5 — Structure (Medium)
- `database_helper.dart` (1,409 lines) combines schema creation, migrations, patch loading,
  search-query construction, Tanglish normalisation, and CRUD for six entities. Suggested splits,
  each behaviour-preserving: `migrations.dart` (v3–v6), `search_queries.dart` (LIKE builder,
  Tamil variants, Tanglish rules), and per-entity DAOs. `DatabaseHelper` keeps the singleton and
  open logic.
- `song_detail_screen.dart` (1,034 lines) mixes link launching, notes, highlights, verses and the
  Mayuragiri section; the URL-launch methods are four copies of one pattern
  (`_launchYouTubeSearch`, `_launchGoogleSearch`, `_launchCustomUrl`, `_launchMayuragiriUrl`).
  Extract one `_launchWhitelisted(url, hosts, siteName)`.
- Two layers wrap the same calls: `SongRepository` mostly forwards to `DatabaseHelper`, and
  several screens call `DatabaseHelper()` directly (`temple_songs_screen.dart:29` etc.), which
  bypasses `notifyListeners()` and makes UI tests need a real DB. Pick one entry point.
- `AppException` types in `error_handler.dart` (`DatabaseException`, `NetworkException`, …) and a
  second `print`-based logger there duplicate `AppLogger`. Check which are used; the app has no
  network layer, so `NetworkException`/`timeoutError` look dead.
- `lib/constants/app_strings.dart` and the `Paddings`/`BorderRadiuses`/`AppConstants.spacing*`
  trio overlap. Consolidate when next touched.
- `_dbVersion` and `AppConstants.dbVersion`, plus `dbName` / `_dbName`, are duplicated.

### M6 — Dependencies (Medium)
Direct dependencies behind (current → latest), from `flutter pub outdated`:
- `sqlite3_flutter_libs 0.5.38` → `0.6.0+eol`: the package is end-of-life. Investigate whether it
  is still needed (it bundles SQLite for `sqflite_common_ffi` on desktop; mobile uses the system
  SQLite). If only desktop uses it, move desktop-only dependencies out of the Android build path.
- Safe patch/minor bumps with no API change: `sqflite 2.4.5`, `shared_preferences 2.5.6`,
  `path_provider 2.1.6`, `url_launcher 6.3.3`, `timezone 0.11.2`, `flutter_local_notifications
  22.3.2`, `provider 6.1.5+1`.
- Majors needing a look: `file_picker 10 → 13`, `share_plus 11 → 13` (the code already carries
  `// ignore: deprecated_member_use` on `Share.shareXFiles`, so migrate to `SharePlus.instance.share`
  when upgrading), `app_links 6 → 7`, `dynamic_color 1 → 2`, `flutter_lints 5 → 6`.
- `dynamic_color` and `cupertino_icons` are declared but nothing in `lib/` imports or uses them
  (grep for `dynamic_color`, `DynamicColor` and `Cupertino` finds nothing outside generated l10n).
  Candidates to remove. `sqlite3_flutter_libs` is likewise never imported directly; it only
  matters as a transitive native dependency of `sqflite_common_ffi` (desktop).
- `android.enableJetifier=true` is unnecessary when no dependency uses the old support library
  and slows builds; test removing it. `kotlin.incremental=false` also slows builds. The
  `-Xmx8G` JVM setting exceeds many CI/dev machines.

### M7 — Hygiene (Low)
- `main_wrapper.dart:39` has a stray `// ... (omitted AppLinks code) ...` comment above real code.
- `_appLinks.uriLinkStream.listen(...)` is never cancelled (`main_wrapper.dart:118`); cancel it in
  `dispose`.
- `MainWrapper` quits with `exit(0)`; `SystemNavigator.pop()` is the supported way and lets
  Android finish the activity normally.
- `song_repository.dart:1` has a commented-out import; there are two identical
  `// --- Song and Meaning Methods ---` headings.
- `pubspec.yaml` still says `description: "A new Flutter project."` and has blank dependency
  gaps; `flutter_launcher_icons` sets `min_sdk_android: 21` while `minSdk` comes from Flutter.
- Repo hygiene: `scripts/output/mayuragiri_lyrics_separated.json` (59k lines) is tracked and
  `scripts/__pycache__` exists locally (`*.pyc` is ignored, fine). Move the large generated
  output out of git or document how it is regenerated. `.git` is 79 MB largely because of
  repeated 38 MB DB revisions; avoid re-committing the DB unless it changes.
- Docs: `docs/database.md` is current (v6). `docs/architecture.md` and `docs/setup.md` should be
